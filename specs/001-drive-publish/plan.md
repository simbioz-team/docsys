# План — 001 Выгрузка в Google Drive

## Устройство

```
plugins/docsys/scripts/
  publish.py          CLI: выгрузка, --dry-run, status, auth; хук зовёт его с путём
  publish_render.py   что выгрузить: отбор (R2–R3), имя (R5), шапка (R6),
                      ссылки (R7), путь папки (R8), хеш (R10) — без сети
  gdrive.py           как выгрузить: OAuth (R18), запросы Drive v3 (R21–R22)
  on-doc-edit.sh      + фоновый вызов publish.py и сообщение о провале (R13–R14)
plugins/docsys/commands/doc-publish.md
tests/
  fake_drive.py       поддельный Drive v3 + токен-сервер на http.server
  test_publish.py     unittest: сценарии из «Готовности» п. 2
```

Деление `publish_render` / `gdrive` — граница «что» и «как»: рендер чистый,
тестируется без сервера; второй поставщик заменит только `gdrive.py`.

## Алгоритм выгрузки

1. Конфиг, `publish` нет → выход 0 молча.
2. Блокировка `.git/docsys-publish.lock` (`fcntl.flock`, ожидание до 60 с).
3. Токен доступа: refresh_token → `oauth2/token`.
4. Список всех файлов Drive с `properties has {key='docsys_root' and value='<folder_id>'}`
   и `trashed=false` → карта `docsys_id → {id, hash, parents, name}`.
   Одной пачкой запросов (пагинация), а не поиском на каждый документ.
5. План: документы к выгрузке (R2–R3). Для полного прогона — все; для хука —
   один путь.
6. Проход 1 — ID: у каждого документа плана без файла в Drive создаётся пустой
   Google Doc в нужной папке со свойствами (`docsys_hash` пустой). Так у
   всех выгружаемых документов есть ID до рендера ссылок.
   - Для одиночной выгрузки ссылки на ещё не выгруженные документы → «в
     репозитории» (R7); при полной выгрузке они появятся, R10 перевыгрузит.
7. Проход 2 — содержимое: рендер (шапка + тело с переписанными ссылками),
   хеш; совпал с `docsys_hash` и имя то же → пропуск; иначе
   `files.update` (multipart: метаданные + `text/markdown`), с новым хешем и
   именем; папка не та → `addParents/removeParents`.
8. Архив (только полный прогон): файлы Drive с `docsys_id`, которых нет среди
   плана, и не в `Архив` → перенос в `Архив`.
9. Итог в `.git/docsys-publish.status` (`ok`/`fail` + текст), строка в журнал.

Папки: кеш `путь → id` за прогон; поиск папки — по имени и родителю
(`mimeType = folder`), нет — создать.

## Хук

После пересборки реестров:

1. Есть `.git/docsys-publish.status` с `fail` и без отметки «показано» →
   напечатать строку и отметить.
2. Документ подлежит выгрузке и есть `publish` и токен →
   `nohup python3 publish.py --path <rel> >> .git/docsys-publish.log 2>&1 &`.

Проверка «подлежит» — в `publish.py --should <rel>` нельзя: лишний процесс
питона на каждую правку. Делается в том же питоне, что уже решает «документ
ли это», — он печатает два флага.

## Ссылки (R7)

Разбор — тем же выражением, что `check_doc_links.MD_LINK`, но с картинками
(`!\[…\](…)`). Путь цели — от каталога документа, нормализуется к пути от
корня. Цель в плане → ID; цель — документ вне плана или файл → текст с путём.

## Конвертация

Создание: `POST upload/drive/v3/files?uploadType=multipart`, метаданные
`mimeType: application/vnd.google-apps.document`, медиа `text/markdown`.
Обновление: `PATCH upload/drive/v3/files/<id>?uploadType=multipart`, медиа
`text/markdown`. Риск из спеки — проверить первым на живом диске.
