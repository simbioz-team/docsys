# docsys — система документации как плагин

Репозиторий-маркетплейс с одним плагином. Прикладного кода нет.

## Раскладка

- `plugins/docsys/commands/` — семь команд `/doc-*`, плоские md
- `plugins/docsys/skills/doc-system/` — справочник: контракт метаданных,
  статусы, tier, устройство реестров
- `plugins/docsys/scripts/` — код проверок и сборки реестров
- `plugins/docsys/templates/` — шаблоны типов документов

## Правила работы

- **Зависимости — только `bash`, `git`, `python3`.** Ни PyYAML, ни jq: плагин
  ставится на чужие машины и в CI. Поэтому конфиг — JSON.
- **Корень проекта не выводится из места скрипта.** Внутри плагина скрипт лежит
  вне проверяемого репозитория. Ищи через `docs_lib.find_root()` или `cwd`.
  Это уже ломалось при переносе: три скрипта считали `__file__.parent.parent`
  корнем и проверяли каталог плагина.
- **Хуки читают рабочую директорию из `cwd` входного JSON**, не из
  `${CLAUDE_PROJECT_DIR}`: в worktree-сессии второе остаётся на основном checkout.
- **Хук — no-op без `.claude/doc-config.json`.** Плагин молчит там, где систему
  не разворачивали.
- **Отсутствующее поле — прочерк, а не догадка.** Правило действует и в коде, и
  в инструкциях команд. Реестр обязан отражать источник.
- Меняешь состав команд или проверок — правь таблицы в `README.md` и справочник
  в `skills/doc-system/SKILL.md`.

## Проверка после правок

```bash
python3 -m py_compile plugins/docsys/scripts/*.py
bash -n plugins/docsys/scripts/*.sh
python3 -c "import json,glob;[json.load(open(f)) for f in glob.glob('**/*.json',recursive=True)]"
```

Скрипты проверяются на настоящем дереве документов, а не на вид: заведите
песочницу с документами, сломайте по одному правилу и убедитесь, что каждое
ловится.

## Релиз

Версия плагина в `plugin.json` **пинит** его для тех, кто ставит с GitHub: пока
строка та же, Claude Code считает плагин свежим и оставляет пользователю
закэшированную копию. Забыли поднять — изменения не доехали, и никто этого не
заметит.

Порядок:

1. Поднять `version` в `plugins/<имя>/.claude-plugin/plugin.json`.
2. Дописать раздел в `CHANGELOG.md`.
3. Закоммитить, запушить.
4. `claude plugin tag plugins/<имя> --push -m "<имя> %s"` — создаёт тег
   `<имя>--v<версия>` и проверяет, что манифест плагина и запись в маркетплейсе
   не разошлись.
5. `gh release create <имя>--v<версия> --notes-from-tag` — чтобы версия была
   видна на GitHub, а не только в списке тегов.

Правило нумерации, пока `0.x`: **минор — ломающее, патч — всё остальное.**

Что ломающее для плагина:

- убрали или переименовали команду;
- во frontmatter появилось новое обязательное поле;
- несовместимо изменилась схема конфига;
- **добавили проверку-гейт** — формально это добавление, фактически проект,
  который был зелёным, краснеет после обновления.

Последний случай неочевиден и встречается чаще прочих. Смягчить можно
храповиком (как в проверке ссылок) или сделав проверку отчётом, а не гейтом
(как свежесть).

В PR это сторожит `.github/workflows/version.yml`: менялись файлы плагина, а
`version` нет — сборка краснеет.
## Чего не делать

- Не тянуть обратно специфику исходного продукта: персоны, типы документов под
  конкретную предметную область, привязку tier к spec-kit.
- Не заставлять агента перестраивать реестры вручную — для этого есть скрипт,
  и в этом весь смысл.
- Не делать свежесть гейтом по умолчанию: отставание — повод посмотреть, а не
  запрет коммита.
