# docsys

Система проектной документации для ИИ-агентов. Плагин Claude Code.

Выросла на корпусе в ~800 документов, где сплошное чтение не помещается ни в
один контекст. Здесь — переносимое ядро, без специфики проекта, в котором
система появилась.

## Зачем

Три задачи, которые документация решает именно для агента:

1. **Найти нужное, не читая всё.** Поиск идёт по машинному реестру, сам документ
   открывается после того, как отобран.
2. **Не опереться на неправду.** Статус документа говорит, можно ли на него
   опираться, и это проверяется, а не декларируется.
3. **Заметить расхождение с кодом.** Документ, который не врёт по форме, но
   описывает прошлое, — самый дорогой вид неправды.

## Установка

```
/plugin marketplace add simbioz-team/docsys
/plugin install docsys@docsys
```

Локально:

```
/plugin marketplace add /home/rustam/develop/simbioz_team/docsys
/plugin install docsys@docsys
```

Затем в проекте:

```
/doc-init
```

## Команды

| Команда | Что делает |
|---|---|
| `/doc-init` | развернуть систему в проекте: конфиг, каталоги, реестры, гейт |
| `/doc-new` | создать документ из шаблона и зарегистрировать |
| `/doc-update` | изменить документ и привести метаданные в порядок |
| `/doc-sync` | пересобрать реестры, показать правки без обновлённых метаданных |
| `/doc-search` | найти по реестру, не читая документы |
| `/doc-validate` | прогнать проверки и разобрать находки |
| `/doc-audit` | разобрать один документ на качество содержания |
| `/doc-publish` | выгрузить документы в Google Drive для сотрудников без доступа к репозиторию |

## Два реестра

| Файл | Для кого | Что внутри |
|---|---|---|
| `docs/INDEX.md` | человек и агент | счётчики по разделам и статусам + таблица со ссылками |
| `docs/TAGS.md` | машина | `path \| scope \| type \| tier \| status \| updated \| tags \| title \| summary` |

Оба собираются скриптом и руками не правятся. В них входят документы
`docs/` и дополнительных корней (`extra_roots`, например спеки
`specs/*/spec.md`) — см. «Несколько корней».

**Сборка детерминирована** — одно и то же дерево документов даёт побайтово
одинаковый вывод. Отсюда два следствия: расхождение ловится сравнением
(`--check`), а отсутствующее поле становится прочерком, а не правдоподобной
догадкой.

Это главное отличие от первой версии системы, где реестры перестраивал сам
агент по инструкции. Прецедент оттуда: пятнадцати документам вписали `status: active`,
которого в источнике не было — документы стали выглядеть актуальными, а
проверочный хук их не трогал вовсе, потому что условие требовало полей, которых
у них нет. Требования устарели незаметно.

## Проверки

```bash
python3 scripts/check_docs.py            # всё
python3 scripts/check_docs.py --only frontmatter
python3 scripts/check_docs.py --strict   # свежесть тоже гейт
```

| Проверка | Что ловит | Гейт |
|---|---|---|
| `frontmatter` | значение поля вне словаря конфига, битая дата, документ не в своём каталоге, недозаполненный шаблон | да |
| `registries` | реестры разошлись с документами | да |
| `status` | статус в теле (`## Status` или `- **status:**`) ≠ frontmatter; `active` adr/spec ссылается на `draft` или мёртвое — в том числе через границу корней | да |
| `links` | ссылка не открывается; ссылки в `specs/` проверяются, когда `specs` — доп. корень | да, с храповиком |
| `freshness` | документ отстал от кода, который описывает | нет, отчёт |

**Храповик ссылок** (`.claude/doc-links-baseline.json`): известные битые ссылки
не блокируют работу, но множество может только сокращаться. Так живой проект с
накопленным долгом ставится под проверку, не останавливая работу.

**Свежесть** сравнивает дату последнего коммита в документ с датой последнего
коммита в код из поля `related_code:`. Без этого поля документ для сверки
невидим — честнее ложной тревоги по догадке о том, что он описывает.

## Проверки в CI

В раннере CI плагина нет. Стандарт — неглубокий клон по тегу и `DOCSYS_HOME`
на каталог плагина; `check.sh` из `/doc-init` берёт путь оттуда:

```yaml
- name: docsys
  run: |
    git clone --depth 1 --branch docsys--v0.3.1 \
      https://github.com/simbioz-team/docsys "$RUNNER_TEMP/docsys"
    echo "DOCSYS_HOME=$RUNNER_TEMP/docsys/plugins/docsys" >> "$GITHUB_ENV"
```

Версию тега держат той же, что у разработчиков. Не копия `scripts/` в проект —
она молча отстанет; не сабмодуль — трение у каждого ради одного шага CI.

## Хук

`PostToolUse` на правку `*.md` под `docs/` или по шаблону `extra_roots`
пересобирает реестры автоматически. Правка `plan.md` рядом со спекой — нет: это
не документ. Файл из `exclude` (журнал, рабочие материалы) — тоже нет.
Молчит, если в проекте нет `.claude/doc-config.json`: плагин не навязывается
там, где систему не разворачивали.

Если настроена выгрузка (`publish`), тот же хук выгружает правленый документ
в Google Drive — в фоне, не задерживая агента. О провале сообщает при
следующей правке, одной строкой.

## Выгрузка в Google Drive

Сотрудники без доступа к репозиторию читают документы как Google Docs:
открыть по ссылке, скачать в docx или pdf, прокомментировать.

- **Поток в одну сторону, git → Drive.** Документ в Drive перезаписывается
  целиком; обратно ничего не идёт. Замечания — комментариями, в git их вносят люди.
- **Что выгружается** — документы из `publish.include` (по умолчанию все), кроме
  `publish.exclude` и статусов из `skip_statuses` (по умолчанию `archived`).
- **Как выглядит** — Google Doc с шапкой: статус, тип, дата, путь в репозитории;
  у черновика метка в имени и предупреждение. Ссылки на выгруженные документы
  ведут в Drive, на прочие файлы — текстом с путём. Папки повторяют репозиторий.
- **Что исчезло из репозитория** — копия уходит в папку `Архив`, не удаляется.
- **Где помнит связь** — в свойствах файлов Drive, локального состояния нет.

Настройка — в `/doc-publish`: папка (общий диск или личный), OAuth-клиент «Desktop app», раздел
`publish` в конфиге, вход. Токен — у пользователя в `~/.config/docsys/`.

## Конфиг

`.claude/doc-config.json` — JSON, а не YAML, как было в первой версии.
Причина: YAML не в стандартной библиотеке, а PyYAML пришлось бы ставить в каждый
проект и в каждый CI. Пример — в `/doc-init`.

## Несколько корней

Документы не обязаны жить в одном `docs/`. Спеки, которые speckit раскладывает
в `specs/NNN-slug/spec.md`, входят в систему на месте:

```json
"types": [ { "name": "spec", "template": "spec.md", "path": "specs/{NNN}-{slug}/spec.md" } ],
"extra_roots": [ { "glob": "specs/*/spec.md" } ]
```

Корень — шаблон файлов, а не каталог: `plan.md` и `tasks.md` рядом со спекой
остаются рабочими материалами. Без `extra_roots` поведение прежнее.

## Связь с muagba-pro

Независимы, но стыкуются: шаблон [muagba-pro](../muagba-pro) уже несёт
`docs/INDEX.md` и `docs/TAGS.md`, а его `.claude/check.sh` — то место, куда
`/doc-init` добавляет строку с `check_docs.py`.

## Требования

`bash`, `git`, `python3`. Ничего больше. Выгрузка в Drive — тоже: HTTP через
стандартную библиотеку.

## Тесты

```bash
python3 -m unittest discover -s tests -v
```

Выгрузка проверяется на поддельном Drive (`tests/fake_drive.py`) — локальном
HTTP-сервере с тем подмножеством API, которым пользуется плагин.

## Что сознательно не вошло

Синтетические персоны, привязка `tier` к конституции spec-kit, типы документов
под конкретный продукт (`feature-overview`, `screen`, `screen-flow`, `cjm`),
команды экспорта и импорта, проверка покрытия API-эндпоинтов документацией.

Всё это работает, но предполагает устройство одного конкретного продукта.
Ядро должно ставиться на любой проект.
